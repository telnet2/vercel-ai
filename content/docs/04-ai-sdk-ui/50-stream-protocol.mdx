# Stream Protocols

AI SDK UI functions such as `useChat` and `useCompletion` support both text streams and data streams.
The stream protocol defines how the data is streamed to the frontend on top of the HTTP protocol.

This page describes both protocols and how to use them in the backend and frontend.

You can use this information to develop custom backends and frontends for your use case, e.g.,
to provide compatible API endpoints that are implemented in a different language such as Python.

For instance, here's an example using [FastAPI](https://github.com/vercel/ai/tree/main/examples/next-fastapi) as a backend.

## Text Stream Protocol

A text stream contains chunks in plain text, that are streamed to the frontend.
Each chunk is then appended together to form a full text response.

Text streams are supported by `useChat`, `useCompletion`, and `useObject`.
When you use `useChat` or `useCompletion`, you need to enable text streaming
by setting the `streamProtocol` options to `text`.

You can generate text streams with `streamText` in the backend.
When you call `toTextStreamResponse()` on the result object,
a streaming HTTP response is returned.

<Note>
  Text streams only support basic text data. If you need to stream other types
  of data such as tool calls, use data streams.
</Note>

### Text Stream Example

Here is a Next.js example that uses the text stream protocol:

```tsx filename='app/page.tsx'
'use client';

import { useChat } from '@ai-sdk/react';
import { TextStreamChatTransport } from 'ai';
import { useState } from 'react';

export default function Chat() {
  const [input, setInput] = useState('');
  const { messages, sendMessage } = useChat({
    transport: new TextStreamChatTransport({ api: '/api/chat' }),
  });

  return (
    <div className="flex flex-col w-full max-w-md py-24 mx-auto stretch">
      {messages.map(message => (
        <div key={message.id} className="whitespace-pre-wrap">
          {message.role === 'user' ? 'User: ' : 'AI: '}
          {message.parts.map((part, i) => {
            switch (part.type) {
              case 'text':
                return <div key={`${message.id}-${i}`}>{part.text}</div>;
            }
          })}
        </div>
      ))}

      <form
        onSubmit={e => {
          e.preventDefault();
          sendMessage({ text: input });
          setInput('');
        }}
      >
        <input
          className="fixed dark:bg-zinc-900 bottom-0 w-full max-w-md p-2 mb-8 border border-zinc-300 dark:border-zinc-800 rounded shadow-xl"
          value={input}
          placeholder="Say something..."
          onChange={e => setInput(e.currentTarget.value)}
        />
      </form>
    </div>
  );
}
```

```ts filename='app/api/chat/route.ts'
import { streamText, UIMessage, convertToModelMessages } from 'ai';
__PROVIDER_IMPORT__;

// Allow streaming responses up to 30 seconds
export const maxDuration = 30;

export async function POST(req: Request) {
  const { messages }: { messages: UIMessage[] } = await req.json();

  const result = streamText({
    model: __MODEL__,
    messages: await convertToModelMessages(messages),
  });

  return result.toTextStreamResponse();
}
```

## UI Message Stream Protocol

The UI Message Stream Protocol defines how AI responses are streamed from server to browser using Server-Sent Events (SSE). It provides real-time streaming of text, reasoning, tool invocations, files, sources, and custom data parts.

<Note>
  When you provide data streams from a custom backend, you need to set the
  `x-vercel-ai-ui-message-stream` header to `v1`.
</Note>

### Transport Layer

The protocol uses **Server-Sent Events (SSE)** as the underlying transport mechanism.

#### HTTP Headers

```http
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
X-Vercel-AI-UI-Message-Stream: v1
X-Accel-Buffering: no
```

The `X-Accel-Buffering: no` header disables nginx buffering for proper streaming.

#### Wire Format

Each message chunk is encoded as a JSON object prefixed with `data: ` and terminated with double newlines:

```
data: {"type":"text-start","id":"text-1"}\n\n
data: {"type":"text-delta","id":"text-1","delta":"Hello"}\n\n
data: {"type":"text-delta","id":"text-1","delta":" world"}\n\n
data: {"type":"text-end","id":"text-1"}\n\n
data: {"type":"finish","finishReason":"stop"}\n\n
data: [DONE]\n\n
```

The stream terminates with `[DONE]` marker.

### Flow Control Parts

#### Message Start Part

Initializes the stream and optionally sets message ID and metadata.

```ts
{
  type: "start";
  messageId?: string;          // Unique message identifier
  messageMetadata?: unknown;   // Custom metadata for the message
}
```

Example:

```
data: {"type":"start","messageId":"msg-123"}

```

#### Finish Message Part

Signals stream completion with finish reason and optional usage statistics.

```ts
{
  type: "finish";
  finishReason?: "stop" | "length" | "content-filter" | "tool-calls" | "error" | "other";
  usage?: LanguageModelUsage;  // Token usage statistics
  messageMetadata?: unknown;
}
```

The `usage` field contains token usage information:

```ts
{
  inputTokens: number | undefined;
  inputTokenDetails: {
    noCacheTokens: number | undefined;
    cacheReadTokens: number | undefined;
    cacheWriteTokens: number | undefined;
  };
  outputTokens: number | undefined;
  outputTokenDetails: {
    textTokens: number | undefined;
    reasoningTokens: number | undefined;
  };
  totalTokens: number | undefined;
}
```

Example:

```
data: {"type":"finish","finishReason":"stop","usage":{"inputTokens":10,"outputTokens":25,"totalTokens":35}}

```

#### Abort Part

Signals stream was aborted with an optional reason.

```ts
{
  type: "abort";
  reason?: string;             // Optional abort reason
}
```

Example:

```
data: {"type":"abort","reason":"user cancelled"}

```

#### Message Metadata Part

Updates message metadata during streaming.

```ts
{
  type: "message-metadata";
  messageMetadata: unknown;
}
```

Example:

```
data: {"type":"message-metadata","messageMetadata":{"custom":"data"}}

```

### Text Parts

Text content is streamed using a start/delta/end pattern with unique IDs to support multiple concurrent text parts.

#### Text Start Part

Begins a new text part.

```ts
{
  type: "text-start";
  id: string;                           // Unique identifier for this text part
  providerMetadata?: ProviderMetadata;  // Provider-specific metadata
}
```

Example:

```
data: {"type":"text-start","id":"text-1"}

```

#### Text Delta Part

Appends text content to an active text part.

```ts
{
  type: "text-delta";
  id: string;                           // Must match a text-start id
  delta: string;                        // Text content to append
  providerMetadata?: ProviderMetadata;
}
```

Example:

```
data: {"type":"text-delta","id":"text-1","delta":"Hello"}

```

#### Text End Part

Finalizes a text part.

```ts
{
  type: "text-end";
  id: string;                           // Must match a text-start id
  providerMetadata?: ProviderMetadata;
}
```

Example:

```
data: {"type":"text-end","id":"text-1"}

```

### Reasoning Parts

Extended thinking/reasoning content follows the same pattern as text.

#### Reasoning Start Part

Begins a reasoning block.

```ts
{
  type: "reasoning-start";
  id: string;
  providerMetadata?: ProviderMetadata;
}
```

Example:

```
data: {"type":"reasoning-start","id":"reasoning-1"}

```

#### Reasoning Delta Part

Appends reasoning content.

```ts
{
  type: "reasoning-delta";
  id: string;
  delta: string;
  providerMetadata?: ProviderMetadata;
}
```

Example:

```
data: {"type":"reasoning-delta","id":"reasoning-1","delta":"Let me think..."}

```

#### Reasoning End Part

Finalizes a reasoning block.

```ts
{
  type: "reasoning-end";
  id: string;
  providerMetadata?: ProviderMetadata;
}
```

Example:

```
data: {"type":"reasoning-end","id":"reasoning-1"}

```

### Tool Invocation Parts

Tool calls support streaming input arguments, approval workflows, and output results.

#### Tool Input Start Part

Begins a tool invocation.

```ts
{
  type: "tool-input-start";
  toolCallId: string;                   // Unique identifier for this tool call
  toolName: string;                     // Name of the tool being invoked
  providerExecuted?: boolean;           // True if provider will execute the tool
  providerMetadata?: ProviderMetadata;  // Provider-specific metadata
  dynamic?: boolean;                    // True for dynamic (runtime-registered) tools
  title?: string;                       // Human-readable title for the tool call
}
```

Example:

```
data: {"type":"tool-input-start","toolCallId":"call-1","toolName":"getWeather"}

```

#### Tool Input Delta Part

Streams partial JSON input arguments.

```ts
{
  type: "tool-input-delta";
  toolCallId: string;
  inputTextDelta: string;               // Partial JSON string to append
}
```

The client uses partial JSON parsing to extract incomplete objects for UI updates.

Example:

```
data: {"type":"tool-input-delta","toolCallId":"call-1","inputTextDelta":"{\"location\":\"San Francisco\"}"}

```

#### Tool Input Available Part

Signals complete, validated tool input is ready.

```ts
{
  type: "tool-input-available";
  toolCallId: string;
  toolName: string;
  input: unknown;                       // Complete, parsed input object
  providerExecuted?: boolean;
  providerMetadata?: ProviderMetadata;
  dynamic?: boolean;
  title?: string;
}
```

Example:

```
data: {"type":"tool-input-available","toolCallId":"call-1","toolName":"getWeather","input":{"location":"San Francisco"}}

```

#### Tool Input Error Part

Signals an error occurred during input parsing.

```ts
{
  type: "tool-input-error";
  toolCallId: string;
  toolName: string;
  input: unknown;                       // Partial or invalid input
  errorText: string;                    // Error description
  providerExecuted?: boolean;
  providerMetadata?: ProviderMetadata;
  dynamic?: boolean;
  title?: string;
}
```

Example:

```
data: {"type":"tool-input-error","toolCallId":"call-1","toolName":"getWeather","input":{},"errorText":"Missing required field: location"}

```

#### Tool Approval Request Part

Requests user approval before tool execution.

```ts
{
  type: "tool-approval-request";
  approvalId: string;                   // Unique identifier for this approval request
  toolCallId: string;
}
```

Example:

```
data: {"type":"tool-approval-request","approvalId":"approval-1","toolCallId":"call-1"}

```

#### Tool Output Available Part

Provides tool execution result.

```ts
{
  type: "tool-output-available";
  toolCallId: string;
  output: unknown;                      // Tool execution result
  providerExecuted?: boolean;
  dynamic?: boolean;
  preliminary?: boolean;                // True if this is a partial/streaming result
}
```

Example:

```
data: {"type":"tool-output-available","toolCallId":"call-1","output":{"temperature":18,"condition":"sunny"}}

```

#### Tool Output Error Part

Signals tool execution failed.

```ts
{
  type: "tool-output-error";
  toolCallId: string;
  errorText: string;                    // Error description
  providerExecuted?: boolean;
  dynamic?: boolean;
}
```

Example:

```
data: {"type":"tool-output-error","toolCallId":"call-1","errorText":"API rate limit exceeded"}

```

#### Tool Output Denied Part

Signals user denied tool execution approval.

```ts
{
  type: "tool-output-denied";
  toolCallId: string;
}
```

Example:

```
data: {"type":"tool-output-denied","toolCallId":"call-1"}

```

### Source Parts

References to source materials.

#### Source URL Part

Web URL reference.

```ts
{
  type: "source-url";
  sourceId: string;
  url: string;
  title?: string;
  providerMetadata?: ProviderMetadata;
}
```

Example:

```
data: {"type":"source-url","sourceId":"src-1","url":"https://example.com","title":"Example Page"}

```

#### Source Document Part

Document reference.

```ts
{
  type: "source-document";
  sourceId: string;
  mediaType: string;                    // IANA media type
  title: string;
  filename?: string;
  providerMetadata?: ProviderMetadata;
}
```

Example:

```
data: {"type":"source-document","sourceId":"doc-1","mediaType":"application/pdf","title":"Report"}

```

### File Part

File attachment.

```ts
{
  type: "file";
  url: string;                          // URL or Data URL
  mediaType: string;                    // IANA media type
  providerMetadata?: ProviderMetadata;
}
```

Example:

```
data: {"type":"file","url":"https://example.com/image.png","mediaType":"image/png"}

```

### Step Boundary Parts

For multi-step reasoning workflows.

#### Start Step Part

Marks the beginning of a new reasoning step.

```ts
{
  type: "start-step";
}
```

Example:

```
data: {"type":"start-step"}

```

#### Finish Step Part

Marks the end of a reasoning step. Resets active text and reasoning parts.

This part is necessary to correctly process multiple stitched assistant calls, e.g. when calling tools in the backend, and using steps in `useChat` at the same time.

```ts
{
  type: "finish-step";
}
```

Example:

```
data: {"type":"finish-step"}

```

### Data Parts

Custom data parts with dynamic type names.

```ts
{
  type: `data-${string}`;               // e.g., "data-weather", "data-chart"
  id?: string;                          // Optional ID for updates
  data: unknown;                        // Custom payload
  transient?: boolean;                  // If true, not persisted to message state
}
```

Data parts with the same `type` and `id` will update existing parts instead of creating new ones.

Example:

```
data: {"type":"data-weather","data":{"location":"SF","temperature":72}}

```

### Error Part

Error notification.

```ts
{
  type: "error";
  errorText: string;
}
```

Example:

```
data: {"type":"error","errorText":"An error occurred"}

```

### Provider Metadata

Optional provider-specific metadata can be attached to chunks:

```ts
type ProviderMetadata = Record<string, Record<string, JSONValue | undefined>>;
```

Example:

```json
{
  "anthropic": {
    "cacheControl": "ephemeral"
  }
}
```

### UI Message Stream Example

The data stream protocol is supported by `useChat` and `useCompletion` on the frontend and used by default.
`useCompletion` only supports the `text` and `data` stream parts.

On the backend, you can use `toUIMessageStreamResponse()` from the `streamText` result object to return a streaming HTTP response.

Here is a Next.js example that uses the UI message stream protocol:

```tsx filename='app/page.tsx'
'use client';

import { useChat } from '@ai-sdk/react';
import { useState } from 'react';

export default function Chat() {
  const [input, setInput] = useState('');
  const { messages, sendMessage } = useChat();

  return (
    <div className="flex flex-col w-full max-w-md py-24 mx-auto stretch">
      {messages.map(message => (
        <div key={message.id} className="whitespace-pre-wrap">
          {message.role === 'user' ? 'User: ' : 'AI: '}
          {message.parts.map((part, i) => {
            switch (part.type) {
              case 'text':
                return <div key={`${message.id}-${i}`}>{part.text}</div>;
            }
          })}
        </div>
      ))}

      <form
        onSubmit={e => {
          e.preventDefault();
          sendMessage({ text: input });
          setInput('');
        }}
      >
        <input
          className="fixed dark:bg-zinc-900 bottom-0 w-full max-w-md p-2 mb-8 border border-zinc-300 dark:border-zinc-800 rounded shadow-xl"
          value={input}
          placeholder="Say something..."
          onChange={e => setInput(e.currentTarget.value)}
        />
      </form>
    </div>
  );
}
```

```ts filename='app/api/chat/route.ts'
import { streamText, UIMessage, convertToModelMessages } from 'ai';
__PROVIDER_IMPORT__;

// Allow streaming responses up to 30 seconds
export const maxDuration = 30;

export async function POST(req: Request) {
  const { messages }: { messages: UIMessage[] } = await req.json();

  const result = streamText({
    model: __MODEL__,
    messages: await convertToModelMessages(messages),
  });

  return result.toUIMessageStreamResponse();
}
```
